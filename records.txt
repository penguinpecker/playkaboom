1. ONE-PARAGRAPH SUMMARY
================================================================================

PlayKaboom is a provably-fair on-chain Mines casino on Solana. Players bet
SOL, the server commits a SHA-256 hash of the mine layout up front, signs each
tile reveal during play, and publishes (layout, salt) at settlement so anyone
can verify the layout pre-existed the reveal sequence. The vault that backs
player payouts is a permissionless yield vehicle: anyone can deposit SOL and
receive `units` (an LP position) that share the casino's net P&L pro-rata.
Withdrawals queue for 3 days, units stay live during cooldown (still earning
or losing), and 50% of every settle's house profit is retained in the vault
(boosting unit_value for all LPs); the other 50% goes to a Squads multisig
treasury. The house operates as one of the LPs, with a configurable minimum
share floor (default 50%, decreasing over time). Every privileged operation
requires a 2-of-2 Squads multisig signature; the hot signing key (per-game
reveals) lives on a Turnkey HSM and never touches a server.

2. HIGH-LEVEL ARCHITECTURE
================================================================================

Five-layer stack:

  Layer 1 — Solana program (Anchor 0.31.1, Rust)
            Program ID: 4rPEGzWoD2i8k3Pr5tnJsBV7AZEK2zQJCXZe4YgwcixT (devnet)
            Source: programs/kaboom/src/lib.rs (~2200 LOC)
            Cluster: devnet (mainnet not yet deployed)

  Layer 2 — TypeScript SDK
            packages/sdk/  — instruction builders, account decoders, event
            decoders, PDA helpers. Hand-rolled, no Anchor IDL on the client.

  Layer 3 — Server-side Next.js API
            apps/web/src/app/api/  — Privy-authed routes for player game flow
            (commit/reveal/settle/cleanup) and LP flow (vault/{state,position,
            deposit,request-withdraw,cancel-withdraw,complete-withdraw}).
            apps/web/src/server/ — server-only helpers: env, auth, session,
            game-rng, solana-tx-sender, turnkey-signer, vault-math.

  Layer 4 — Client (Next.js 15 + React 19 + Tailwind)
            apps/web/src/app/ pages: /, /play, /vault, /leaderboard,
            /referrals, /logs, /verify/[sig], /profile/[wallet].
            Privy embedded wallets + standard wallet adapters.

  Layer 5 — Off-chain indexer
            Helius webhook → /api/webhook/helius → Supabase Postgres.
            Mirrors on-chain state for fast UI queries (leaderboard, history,
            APY series, LP positions). Indexer is downstream of on-chain;
            on-chain is the source of truth.

External services:
  • Privy (player auth + embedded wallets)        — apps/web/src/server/auth.ts
  • Turnkey (HSM for house signer)                — apps/web/src/server/turnkey-signer.ts
  • Squads V4 multisig (owner + treasury)         — devnet program SQDS4ep65...
  • Alchemy (RPC + WebSocket; replaces Helius)    — solana-{devnet,mainnet}.g.alchemy.com/v2/<KEY>
  • GitHub Actions (cron-based indexer poll)      — .github/workflows/index-events.yml @ */5 * * * *
  • Supabase Postgres (indexer cache)             — project ref vrxeqgynejlnmwsifvml (Tokyo)
  • Vercel (Next.js host)                         — playkaboom.gg + www.playkaboom.gg + playkaboom-ten.vercel.app
  • Pyth Hermes (USD price overlay)               — public, no auth
  • Upstash Redis (rate limiting)                 — env-configured

  Helius is no longer in the critical path. The /api/webhook/helius endpoint
  remains as a backup ingestion path (auth-gated by HELIUS_WEBHOOK_AUTH); it
  shares the same `ingestTransactions` core as the cron route, so either can
  feed the indexer.

5. SIGNATURE MODEL — WHO HOLDS WHAT KEY, WHAT DOES IT SIGN
================================================================================

Three key types in the system. Each has its own threat model.

  5.1  Player keys
       Format: standard Solana ed25519, 32-byte secret.
       Held by: each player, via Privy embedded wallets (or external wallet
       adapters). Privy stores keys in user-controlled enclaves; the server
       never sees them.
       Signs: start_game, cash_out, set_referrer, claim_referral,
       refund_expired, close_game, lp_deposit, request_withdraw,
       cancel_withdraw, complete_withdraw, close_lp_position.
       Compromise impact: only that player's funds and active game.

  5.2  House operator key (house_authority)
       Format: standard Solana ed25519, 32-byte public key. The PRIVATE
       key is generated and stored by Turnkey inside a TEE. We never
       extract it; we ask Turnkey to sign on our behalf.
       Held by: Turnkey (Org "Kaboom", id <redacted-turnkey-org-id>).
       Public key: 3TCMevgUMRU86Q96dj2mLELjsTAsZyvUp7Pecr8dQKWL
       Signs: every reveal_tile (per tile), every settle_game (per game).
       Sign throughput: ~165ms per call to Turnkey API per tx.
       Compromise model:
         - To compromise we'd need either Turnkey breach OR the API
           key/secret pair stored in Vercel env (TURNKEY_API_PUBLIC_KEY +
           TURNKEY_API_PRIVATE_KEY — secp256r1 P-256 keypair, 32-byte
           private). API keys can be rotated through Turnkey dashboard.
         - Compromised house_authority cannot drain the vault (cannot
           call update_vault, cannot withdraw_to_treasury, cannot move
           house_units). Worst case: malicious settles emitting fake
           layouts, which would be detected by anyone running the
           public verifier (commitment != SHA-256(layout||count||salt)).

  5.3  Owner / treasury key (Squads multisig)
       Format: Solana ed25519 PDA. The Squads V4 program controls signing
       authority via member approvals; the actual on-chain "signer" is the
       Squads vault PDA, signed for via CPI when both members approve.
       Squads V4 program id: SQDS4ep65T869zMMBKyuUq6aD6EgTu8psMjkvj52pCf
                              (same on devnet AND mainnet; Squads-controlled)
       Multisig PDA (devnet): 7RjsJ7uEzVbU7u7JXoPECuBNjgC1eCeuVmny35pNL2Nz
       Vault PDA (devnet)   : At5oBj3KtiTBRkkquZTL1ceY2KDtz1KckLTuaQFbJjVh
       Members (devnet):
         1. DbR1a1CuqwjrdKU9DD6GMqghAXDypD9FLzHNvLabXpRH (project owner)
         2. HYZzCBLht5BUoKYzJ74q5xW2WXtNt5hdi8ofBZHkL4uW (generated test key,
            private at keypairs/squads-cosigner-devnet.json — gitignored)
       Threshold: 2-of-2.
       For mainnet: project owner has created a real Squads via app.squads.so;
       the cosigner identity is not yet shared with this records file.
       Signs: update_vault, allowlist_add/remove, propose_owner,
       cancel_proposed_owner, initialize_v2, update_v2_config, house_deposit,
       house_*_withdraw, withdraw_to_treasury, AND accept_ownership (the
       Squads vault PDA itself signs as new_owner via CPI).
       Compromise impact: full control over vault config and treasury withdrawals.
       Mitigated by:
         - 2-of-2 quorum
         - propose_owner / accept_ownership two-step (an attacker with one
           signature cannot transfer ownership instantly; they need both)

  9.1  Squads V4 web UI (app.squads.so) only exposes mainnet multisig
       creation. The program itself IS deployed to devnet at the same
       program ID (SQDS4ep65T869...), so devnet multisigs must be created

       multisig is mathematically identical to a UI-created one.

       use https://faucet.solana.com (web faucet) or scripts/turnkey-transfer.ts
       (pulls from the Turnkey HSM float). The CLI airdrop frequently fails.

  9.3  macOS TCC blocks Terminal.app from reading files inside ~/Desktop
       unless explicitly granted. Repo was moved from ~/Desktop/Projects to
       ~/Projects to avoid this entirely.

  9.4  `complete_withdraw` requires waiting the full cooldown (3 days at
       the default config). To exercise it on devnet, owner can call
       `update_v2_config(withdrawCooldownSlots=1)` via Squads to drop the
       cooldown for testing. Production deploy must reset to 648000 before
       cutover.

  9.5  Vercel Hobby plan caps cron jobs to once-daily; minute-cadence
       requires Pro ($20/mo). Workaround: GitHub Actions runs the cron at
       5-min cadence (free-tier minimum). To get sub-minute latency,
       upgrade Vercel to Pro and re-add the `crons` block to vercel.json:
         { "path": "/api/cron/index-events", "schedule": "* * * * *" }
       The route handler is unchanged either way.

  9.5b Helius is no longer required — the cron-based indexer reads logs
       directly from Alchemy RPC via getSignaturesForAddress + getTransaction.
       The /api/webhook/helius endpoint stays live as a fallback; both
       paths converge on `ingestTransactions` in apps/web/src/server/indexer.ts.

  9.6  Solana program upgrades require ~5 SOL of free liquidity on the
       upgrade-authority key (current owner DbR1a1...XpRH) to fund the
       buffer + program-data extension. Phase 1 cost ~3.4 SOL of that;
       Phase 2 cost ~5.4 SOL. Top up before any program upgrade.

  9.7  The on-chain math is integer-only (u128 internally, u64 at the
       SOL boundary). All `× num / den` operations floor-divide. This is
       deposit-favorable for the vault (under-mints user units by ≤1)
       and withdraw-favorable for the vault (under-pays user lamports by
       ≤1). Standard 4626 design; the accumulated dust boosts existing
       LPs proportionally over time.

2026-05-06  Production debugging marathon — the bugs that landed in the live UI
────────────────────────────────────────────────────────────────────────────────

After Phase 3 was declared "shipped", every player-facing button still failed.
Each below was a separate bug with a separate fix; landing them all let the
flow Engage Bet → Sign → Play → Cash Out / Settle complete.

Bug list, in the order they surfaced:

1. CSP missed Alchemy domains.  Commit 6c61a74.
   `connect-src` allowlist had `*.helius-rpc.com` etc. but not
   `*.g.alchemy.com`. Browser refused every RPC call after the Helius→Alchemy
   swap. Also flipped Cross-Origin-Opener-Policy from `same-origin` →
   `same-origin-allow-popups` so Coinbase/Base wallet SDKs (loaded by Privy)
   stop tripping their own console error.

2. Privy access token never attached to authed fetches.  Commit ce8fe81.
   apps/web/src/lib/api.ts's post() helper sent neither `Authorization` header
   nor cookie credentials. Server-side auth.ts looked for either, so every
   /api/commit / /api/reveal / /api/settle / /api/vault/* mutator returned 401.
   Fix: setAuthTokenResolver() global + PrivyAuthBridge component that wires
   `usePrivy().getAccessToken` once at mount; every subsequent post() attaches
   `Authorization: Bearer <privy_token>`.

3. Auth error swallowed.  Commit 6efd9b5.
   The 401 said "User not found" for everything — auth.ts had
   `.catch(() => null)` on getUserById which collapsed every distinct error
   into one. Real underlying error revealed by removing the swallow:
   "Invalid app ID or app secret" (PRIVY_APP_SECRET in env didn't match
   NEXT_PUBLIC_PRIVY_APP_ID). Also added /api/whoami diagnostic endpoint
   that returns env binding view + per-step auth failure reason.

4. PRIVY_APP_SECRET was wrong in env.  Commit 6efd9b5 (env-only).
   Old secret: 5mrFAm…JQRWKk4D5 (88 chars). New (correct) secret:
   <redacted-privy-app-secret> (105 chars). Updated
   in Vercel `production` + `development` and apps/web/.env.local.
   Verified pair valid via direct PrivyClient.getUserById probe — Privy
   now returns "User not found" for fake IDs (correct), previously
   returned "Invalid app ID or app secret" (which is the wrong-credentials
   error code).

5. Alchemy doesn't expose `signatureSubscribe` over WS.  Commit 04d2126.
   web3.js's default `connection.confirmTransaction(...)` listens via WS.
   Alchemy returns "Method 'signatureSubscribe' not found" — wait spins
   until blockhash expires. Every player tx looked stuck.
   Fix: apps/web/src/lib/confirm.ts — polling-based confirm using
   `getSignatureStatuses` (1 s cadence) and `getBlockHeight` (5 s cadence;
   slot advances faster than block-height because of skipped slots, so
   getSlot gives false-expired verdicts). Rate-limit aware: per-call
   try/catch + exponential backoff up to 4 s, hard 90 s deadline. ~108
   calls per worst-case confirmation = ~5,400 CU. Free Alchemy tier
   supports ~2,200 confirmations/month; mainnet plan needs paid tier.

6. SDK decodeGameSession didn't read max_payout (Phase 2 field).  Commit 04d2126.
   Phase 2 added max_payout: u64 carved from the prior _reserved bytes
   on GameSession. SDK's accounts.ts decoder skipped the new u64 entirely
   so every read returned undefined. Fix: read r.u64() after version, add
   maxPayout: bigint to GameSessionAccount.

7. Wrong Privy hook for embedded wallets.  Commit b62ca15.
   `useStandardSignTransaction` is for external Wallet-Standard wallets
   (Phantom, Solflare via the standard interface) and expects pre-serialized
   bytes representing a v0 VersionedTransaction. Project uses Privy embedded
   wallets (config: embeddedWallets.solana.createOnLogin = "all-users") which
   require `useSignTransaction`. The wrong hook surfaced as
   "n.serializeMessage is not a function" because the standard handler tried
   to deserialize our legacy serialized tx as VersionedTransaction (which has
   .serialize() but not .serializeMessage()).
   Fix: use-game-actions.ts and use-vault-lp.ts both switched to
   useSignTransaction (takes Transaction object, returns signed Transaction).

8. BigInt(NaN) crash in useGame.tsx.  Commit 1489acc.
   Line 24 returned `BigInt(Date.parse(\`\${Date.now()}\`))` once status
   flipped to "playing". Date.parse needs a date-formatted string, not a
   unix-ms integer-as-string — so the result was NaN, BigInt(NaN) throws,
   the page crashed on every re-render after the bet landed. Fix:
   BigInt(Date.now()) directly — already a finite integer.

9. games table never populated despite events firing.  Commit d0fdd2b.
   Two compounding bugs:
   (a) games_mine_count_range CHECK rejected mine_count=0; GameWon and
       GameLost events don't carry mine_count (only GameSettled does),
       so indexer used 0 as placeholder. Constraint failed silently
       because `.upsert(...)` returns { error } rather than throwing,
       and the handler ignored the result.
   (b) Win path emits GameSettled in a SEPARATE tx from cash_out (only
       lose path is atomic), so updating `games WHERE signature = sig`
       never matched the win-tx row.
   Fix: migration 20260506000004 relaxes mine_count to 0..12, adds
   `game text` column for the GameSession PDA. Indexer GameWon/GameLost
   stores game alongside outcome+payout; GameSettled UPDATEs by `game`
   not `signature`. Added check() helper that throws on Postgrest errors
   so this class of silent failure cannot recur.

What I should have done differently (lessons):
- READ the Privy hook docs end-to-end before picking one. Privy's typedefs
  literally say "embedded → useSignTransaction; standard → useStandardSignTransaction".
- TREAT @solana/web3.js defaults (Connection, confirmTransaction) as
  suspect on non-default RPCs. Alchemy's docs explicitly note WS limits.
- VERIFY auth-required routes with a synthetic bearer to confirm the
  401 reason matches the *intended* failure mode, not a generic "User not found".
- GREP for known footguns (BigInt(Date., Date.parse on numeric strings,
  silent .catch(() => null)) before declaring "shipped".
- DON'T claim end-to-end verified when only on-chain SDK calls were
  exercised. Privy login, browser wallet popup, real domain redirects
  cannot be driven from CLI; say so.

PART 1 — Recovery-banner bug fix (commit dd19a67)
══════════════════════════════════════════════════════════════════════════════

User report: clicking "Force Quit" after a settled game errored
GameAlreadySettled (custom error 0x1781 = 6017).

Root cause: GameRecoveryBanner unconditionally dispatched
close_unsettled_game for Won/Lost states. That ix has
`require!(!game.settled, ...)` to gate self-recovery to ACTUALLY-stuck
games. Once settle_game has run (the normal end state), the right ix is
plain close_game (rent-only reclaim, no `!settled` guard).

Fix: extend the StuckGameInfo interface with a `settled: boolean` field
(plumbed from /api/session/[player] which already returned it but
nobody consumed it), and branch in the dispatcher:
  Won/Lost & !settled  → close_unsettled_game
  Won/Lost &  settled  → close_game
  Expired              → close_game
  Playing              → refund_expired

Files changed:
  apps/web/src/hooks/use-game-resume.ts
  apps/web/src/components/game/GameRecoveryBanner.tsx

PART 4 — Vercel auto-alias quirk diagnosis + fix
══════════════════════════════════════════════════════════════════════════════

Recurring friction: every `vercel --prod` required a manual
`vercel alias set <new-dpl> www.playkaboom.gg` to actually flip the
live site to the latest deploy.

Root cause: only `playkaboom.gg` (apex) was attached to the project
as a domain. www.playkaboom.gg was NOT a project domain — only an
alias on a specific deploy. So when Vercel auto-rolled the
"production" alias on each new prod deploy, it only updated apex,
never www.

Fix: POST /v10/projects/{id}/domains with body {"name":"www.playkaboom.gg"}
to attach the www subdomain as a proper project domain. Verified by
listing project domains afterward — both apex + www now show up.

Confirmed working: subsequent `vercel --prod` deploys correctly
auto-aliased both domains without manual intervention.
